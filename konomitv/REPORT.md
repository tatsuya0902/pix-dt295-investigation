# 報告：初期データの待機が10秒を超えるとライブ視聴クライアントが削除される

KonomiTV **v0.14.1**で、チューナー準備とエンコーダー起動に約11秒かかると、初回視聴の接続が削除されて映像が届かない事象を確認しました。修正候補と回帰テストを添付します。

## 再現と原因

Ubuntu 26.04.1 LTS、Mirakurunバックエンド、PIX-DT295×2、FFmpegの720p配信です。EPGStationで一方の物理チャンネルを録画しながら、エンコーダー停止状態からKonomiTVで別チャンネルへ接続しました。

初回接続後、約11秒で配信を開始する直前に`Client Disconnected (Timeout)`が発生し、HTTP 200でも映像データが0バイトになりました。再接続すれば受信できました。

`LiveStreamClient.readStreamData()`がQueue待機前の時刻を最終読み取り時刻へ記録し、`LiveStream.writeStreamData()`が10秒超のクライアントを削除します。そのため、出力先の停滞だけでなく、最初の入力データを正常に待っている接続も削除されます。

## 修正候補

`fix.patch`は次の2ファイルです。

- `server/app/streams/LiveStream.py`：Queue待機中のフラグを追加し、データ取得後に最終読み取り時刻を更新。finallyで待機フラグを解除し、タイムアウト判定でデータ待機と出力先の停滞を区別します。
- `server/tests/test_live_stream_client_timeout.py`：初期入力待機、配信途中の入力待機、読まない接続、消費後の停滞、キャンセル、終了通知の6件。

タイムアウトの10秒という数値と、停滞したクライアントの回収は維持します。チャンネル・2台構成・画質・EPG設定は変更せず、再接続や常時keepaliveによる回避も追加していません。

## 検証結果

- モック時計で31秒の初期入力待機を含む6件：**修正前3件失敗、修正後6件すべて成功**。
- `poetry run task lint`：Ruff成功、Pyrightエラー0・既存非推奨警告6件。
- 実機では、最初のデータ到着まで**10.572秒**かかっても、HTTPS接続1回・**再接続0回**のまま受信を開始しました。
- EPGStationの録画映像121.922秒、KonomiTVの別チャンネル配信映像61.061秒。初回データ到着後の受信60.797秒、状態APIの同時録画・ONAir観測区間58.448秒。
- クライアントタイムアウト、エンコーダーRestart、USBエラーは検証区間で0件。録画は予定時刻に正常終了しました。

TS同期・TEI・scramble・CC不連続は0件ですが、全体デコードには録画6行・配信2行の警告等が残りました。開始・停止境界との関係が考えられ、端部を除く区間の厳格デコードはエラー0でした。全編エラー0とは主張しません。ブラウザ画面・実スピーカーでの確認と長期運用試験は未実施です。

## 適用・テスト

配置元の公式v0.14.1リリースアーカイブと元ソースが一致すること、別コピーへの適用後の2ファイルが実機検証したソースと一致することを確認しました。未適用のv0.14.1ツリーで使用してください。

```bash
# リポジトリのルート
git apply --check /path/to/fix.patch
git apply /path/to/fix.patch

cd server
poetry run python -m unittest discover -s tests -p test_live_stream_client_timeout.py -v
poetry run task lint
```

初期化が遅い環境でも初回接続を維持するための修正候補として、ご確認をお願いします。
