# 報告：PIX-DT295の受信停止とAES復号処理の性能改善

PIX-DT295の受信が約10〜11MBで止まる事象を調査し、修正候補をまとめました。添付は復号性能改善・診断・セッション更新失敗の通知と回帰テストです。

## 環境と再現

- Ubuntu 26.04.1 LTS、Proxmox VEのUSBパススルー／仮想xHCI、PIX-DT295×2。
- 対象コミット：`42364ad24f4fbcac2a611e0992d6f08a1cbd360f`。
- CMAKE_BUILD_TYPEおよび対象C_FLAGSの最適化指定は空。
- pixd起動後、受信可能な地上波をpix-tsで30秒指定すると、約56,000〜59,000パケットで出力が止まり、映像は約5.5秒でした。後続で`cmd=5 sub=0 val=4 completion=0x0580`、`PIX_CONTEXT_POLL error=255`、DISCONNECTEDが出る場合もありました。

## 原因と修正候補

受信スレッド上のAES MixColumns／InvMixColumnsがO0で約0.450MiB/sにとどまり、約2MiB/sの入力へ追従できませんでした。同じdt295_streamを使う合成試験で、20.563秒後に32MiBリングが満杯となり、first_error=-11を再現しました。その時点のcompleted_bytesは43,122,688、delivered_bytesは9,633,792でした。

有限体上で等価なxtime／XORの式に置き換え、復号をO0で4.437MiB/s、O2で3.052→25.585MiB/sへ改善しました。同じ30秒の合成試験はcompleted=delivered=62,914,560、first_error=0、peak_pending_blocks=3で完了しました。

`fix.patch`は14ファイルです。主な内容は次のとおりです。

- `src/crypto.c`：AES列演算の等価な高速化。
- `src/dt295_stream.c`、受信アダプター：first_errorの理由、転送量、リング使用、処理時間、停止結果等の診断。
- `dt295_renew_if_due()`失敗を通常受信・SIスキャンで通知。エラーを正常扱いにはしません。
- AES列演算、リング再利用、更新失敗の回帰テストとビルド設定。

暗号形式・鍵・リング容量・非同期USB転送タイムアウトは変更していません。TS再同期の移植やファームウェア自動復旧は含めていません。

## 検証結果

- ビルド、make test、通常ホスト上のCTest **17/17成功**。
- AES有限体比較16,384件、OpenSSL比較8,192件、128MiBリング再利用が成功。
- 同じチューナー・同じpixdで、TS到着後35秒の受信・正常停止・再利用を**3回連続成功**。MPEG-2映像は36.703／36.236／36.036秒。
- 3回ともfirst_error=0、timeouts=0、peak_pending_blocks=9／10／9（容量512）、TS同期・TEI・scramble・CC不連続0件。0x0580・poll error=255・DISCONNECTEDの再発なし。
- 後段アプリケーションを含む構成で、2台による別物理チャンネルの同時録画・配信も確認。

`--time 35`は準備時間も含み、映像26.593秒でした。上記3回は`--time -`で開始し、最初のTS到着後35秒でSIGTERMによる正常停止を行った結果です。

## 留保と適用

元の実機障害発生時のfirst_error統計はなく、当時も-11だったことや、0x0580が二次障害だったことは未確定です。長期連続録画・SIGKILL耐性・BS/CSは未検証です。

実機検証には着手前からのUSB診断ログとidle image転送タイムアウト300→3,000msの変更が併存していました。それらは本パッチに含めていません。クリーンな上記コミットへのパッチ適用は別コピーで確認済みですが、そのクリーン構成だけで実機試験をやり直したものではありません。

対象リポジトリのルートで確認できます。未適用ツリーで使用してください。

```bash
git apply --check /path/to/fix.patch
git apply /path/to/fix.patch
```

性能改善・診断・エラー通知を含む修正候補として、ご確認をお願いします。
